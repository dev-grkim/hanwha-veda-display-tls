# SafeVision - 전광판 제어 및 TLS 통신 서버

> 본 리포지토리는 한화 VEDA 4기 팀 프로젝트 "SafeVision" (팀명: 대홍단감자)의 일부로,
> 5인 팀 프로젝트 중 제가 직접 설계·구현한 전광판 펌웨어/드라이버, TLS 통신 서버, 평면도 변환(OpenCV) 부분만 추출하여 정리한 리포지토리입니다.
>
> 팀 프로젝트 전체 코드: [goodaehong/daehongdan](https://github.com/goodaehong/daehongdan)

## 프로젝트 개요

SafeVision은 공장의 가스·화재를 카메라 영상과 센서로 함께 판정한 뒤, 원인에 맞는 대응(환기팬·밸브·사이렌·전광판)을 자동으로 실행하는 지능형 통합 관제 시스템입니다. Raspberry Pi 4를 중앙 서버로 사용하며, 감지된 위험 단계(경고 → 위험 → 비상)에 따라 대응 장비를 제어합니다.

## 담당 역할

| 구분 | 내용 |
|---|---|
| 전광판 펌웨어 | STM32 기반 전광판 보드(HUB75 LED 매트릭스) 펌웨어 개발 |
| 전광판 드라이버 | 라즈베리파이 ↔ 전광판 보드 간 UART 통신 프로토콜 및 리눅스 측 제어 로직 구현 |
| TLS 서버 | 관제 클라이언트(Qt, Windows)와 서버 간 보안 통신을 위한 TCP/TLS 서버 구축 (OpenSSL, 인증서 지문 고정 검증) |
| 평면도 변환 | OpenCV를 이용해 공장 평면도 이미지를 화재 위치 판정 및 대피경로 계산에 쓰이는 60×60 비트맵으로 변환하는 프로그램 개발 (`evac_map_tools`) |

## 기술 스택

- **언어**: C++17, C
- **하드웨어**: Raspberry Pi 4, STM32F4
- **통신**: TCP/TLS(OpenSSL), UART
- **영상처리**: OpenCV (평면도 → 좌표 비트맵 변환)
- **디스플레이**: HUB75 LED 매트릭스 제어
- **빌드**: CMake, STM32CubeIDE

## 주요 구현 내용

### 전광판 표시 로직 – 원인별 화면 전환

판단 단계(경고 → 위험 → 비상)와 원인(화재 계열 / 가스 계열)에 따라 전광판(HUB75 LED 매트릭스)에
표시할 화면(평상시 화면 / 대피 안내 화면)이 전환되도록 설계했습니다. 서버가 UART로 상태 패킷을
보내면 STM32가 이를 파싱해 화면을 렌더링하는 구조입니다.

**겪었던 문제와 해결**

- 전환화면에서 입력값(1/2)에 따라 대피 화면 ↔ 평상시 화면으로 넘어가야 하는데, 상태 플래그 처리가
  꼬여 화면 전환이 아예 안 되거나, 복귀 시 이전 화재 경보 화면과 평상시 화면이 겹쳐 출력되는 버그가
  있었습니다. 화면 상태를 명확히 구분하는 플래그로 정리해 해결했습니다.
- 가스 농도에 따라 표정·그래프 색상이 바뀌어야 하는데 연동이 안 되어 있던 부분을 가스 농도 값
  기준으로 다시 연결했습니다.
- 손상된 UART 패킷이 들어왔을 때 `g_face`/`g_gasColor` 값이 배열 범위를 벗어나 그대로 인덱스로
  쓰이면서 HardFault(보드 다운)가 발생하는 문제가 있었습니다. 값 범위를 클램프해서 방어했습니다.
- 다만 클램프로 못 막는 예기치 못한 정지(무한루프, 그 외 알 수 없는 HardFault)에 대비해 **하드웨어
  워치독(IWDG)**을 추가로 적용했습니다. 이 보드는 HAL IWDG 드라이버가 비활성 상태라 레지스터를
  직접 제어해 LSI(내부 저속 오실레이터) 기준 약 2초 타이머를 구성했고, 메인 루프가 매 반복마다
  타이머를 리셋(Kick)하도록 했습니다. 루프가 멈추면 Kick이 끊겨 하드웨어가 자동으로 리셋되므로,
  기존에는 전원을 직접 뽑았다 꽂아야 복구되던 상황을 몇 초 내 자동 복구로 바꿨습니다.

### 대피경로 UART 패킷 설계 (STM32 전광판 보드)

전광판 보드와 서버 간 통신을 위해 `[STX][Length][Command][Data...][Checksum][ETX]` 구조의
자체 UART 패킷 프로토콜을 설계했습니다. 화재 위치(`CMD_EVAC_FIRES`)와 대피경로 웨이포인트
(`CMD_EVAC_PATH`)를 별도 명령으로 분리해, 출구마다 개별 패킷으로 전송하고 보드 쪽 RAM 배열에
저장·렌더링하도록 구현했습니다.

**겪었던 문제와 해결**

- 여러 출구의 경로 패킷을 텀 없이 연달아 보내면(`SendAllEvacRoutes`) STM32의 수신 링버퍼(64바이트)가
  넘쳐서 뒤에 오는 패킷 일부가 깨지는 문제가 있었습니다. 패킷을 받을 때마다 무거운 전체 화면
  재렌더를 즉시 돌리던 게 원인이었는데, 이를 없애고 대신 50ms 주기 애니메이션 갱신 루틴이 알아서
  최신 상태를 반영하도록 바꿔 해결했습니다.

### 평면도 → 60×60 비트맵 변환 (OpenCV, evac_map_tools)

공장 평면도 이미지를 입력받아 다익스트라 경로 계산에 쓸 60×60 격자 비트맵으로 변환하는 도구를
개발했습니다. 색상 기반 마스킹(`cv::inRange`)으로 벽(흰색)·전광판(주황)·출구(초록)를 구분해
장애물 마스크를 만들고, `INTER_AREA` 보간으로 축소한 뒤 `threshold`로 다시 이진화해 격자를
확정합니다. 마커 위치는 `findContours` + `moments`로 블롭을 분리해 중심 좌표를 구하고, 벽/경계에
맞춰 스냅 보정합니다.

**겪었던 문제와 해결**

- 서버 쪽 격자 크기(`GRID_SIZE`)가 62로 설정돼 있었는데 STM32 펌웨어는 60×60(HUB75 테두리
  상하좌우 2px씩 제외) 기준으로 짜여 있어, 계산된 경로 좌표가 실제 화면 위치와 어긋나는 문제가
  있었습니다. 두 쪽 기준을 60으로 통일하고, threshold 값도 125→120으로 맞춰 해결했습니다.
- 원본 평면도 이미지의 벽이 얇게 그려진 부분은 60×60으로 축소하는 과정에서 통로처럼 오인식되는
  경우가 있어, 평면도 이미지 자체의 벽 두께를 보정해 노이즈를 줄였습니다.

**정리 — 이 변환이 정확히 동작하기 위한 조건**

여러 시행착오를 거치며 정리한 결과, 평면도 이미지는 아래 조건을 만족해야 60×60 격자로 안정적으로
변환됩니다.

1. **색상은 지정된 범위 안에 solid하게** — 벽은 흰색(RGB 각 채널 200~255), 전광판은 정해진 주황
   범위, 출구는 정해진 초록 범위를 벗어나지 않아야 합니다. 그라데이션·안티앨리어싱이 섞이면
   경계 픽셀이 범위 밖으로 새어나가 장애물로 오분류되거나 마커 자체가 인식되지 않습니다.
2. **벽 두께가 다운샘플 비율을 버틸 만큼 두꺼워야 함** — `threshold` 기준값(120/255, 약 47%)
   때문에, 원본 이미지에서 그리드 한 칸에 대응하는 영역의 절반 가까이를 벽 색이 채워야 그 칸이
   장애물로 확정됩니다. 즉 벽 두께(px)가 최소 "원본 해상도 ÷ 60" 수준은 되어야 축소 후에도
   벽이 사라지지 않습니다 — 실제로 이 기준에 못 미쳐 통로로 오인식되던 사례가 있었습니다.
3. **마커는 독립된 하나의 덩어리여야 함** — 전광판·출구 마커끼리 겹치거나 너무 작으면
   `findContours`가 하나로 합쳐 인식하거나 무게중심이 불안정해집니다. 마커별로 분리된 색 블록으로
   충분한 크기를 확보해야 합니다.
4. **격자 크기·threshold 상수는 서버·펌웨어 양쪽에서 반드시 동일해야 함** — 이건 이미지 자체의
   문제는 아니지만, `EvacPlanner`의 `GRID_SIZE`/`threshold`가 STM32 `main.c`의 하드코딩된 값과
   어긋나면 이미지가 완벽해도 좌표계 자체가 틀어집니다.

```bash
# STM32 펌웨어
# STM32CubeIDE로 stm32_firmware/display_board 를 열거나 CMake로 빌드 후 ST-Link로 플래싱

# 드라이버
cd drivers/stm_uart_display
make && make dt-apply && make load
```
